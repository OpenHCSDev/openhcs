# Completion-driven preparation ownership

PreparationCacheBatch already owns discovery, deduplication, child admission and the four-process limit. Replace its fixed four/four/two waves with one refill-and-drain loop: wait on the active workers' result channels, retire completed workers, and fill available slots. PreparationCacheWorker owns idempotent release of its process/channel lease. Parent preparation and readiness remain on PreparationOperation; child jobs still execute cache work without marking parent readiness.

Alternative owners: RegistryService selects catalog callables and owns catalog persistence; FunctionCatalogPreparation owns the complete preparation request and its cancellation; AutoRegisterRegistryPreparation discovers registry families; PreparationOperation owns identity and successful process-local readiness. None owns the queue of admitted cache workers. PreparationCacheWorker already owns the exact process and completion channel, so early release belongs there. Its resource lifetime is mutable: the previous frozen wrapper could not record release. The release flag is set only after successful process closure; unsuccessful closure remains eligible for cleanup. This is independent of parent kernel readiness.

Two NRA exact-source transactions move the scheduler and then unify refill/drain completion handling. The second stage follows a concrete failure: an ordered final drain waited on a held peer and obscured a failed refilled job. One completion loop now observes ready errors and closes only its owned workers. NRA syntax/source checks are not semantic or global behavioral proof. Scoped R0/R1, real held-worker tests, numerical export parity, actual runtime and installed acceptance are separate gates.

The admitted contract is unchanged: at most four live fork children; only operations declaring persistent child-safe work; unique registry projection; exact owned-worker cleanup; no child claim of parent readiness; and lazy parent/module/callable effect order. Platforms without fork retain the original parent path. A multiprocessing.Pool would serialize tasks and lose support for fork-admitted local/dynamic operation classes; the existing worker owner avoids that change.

Before promotion, saved actual-cold dispatcher durations project 19.60s of fixed-wave critical work versus 12.24s with refill, a possible 7.36s saving. This is a launch-order/duration proxy, not a sound runtime bound: import work, cache interactions and changed contention are not modeled. The actual isolated cold comparisons, not this replay, determine promotion. The earlier native quantile route is rejected because shortening a noncritical first-wave worker did not materially shorten the cold pipeline; its source and negative evidence remain on its separate branch.

Maintenance experiment: an additional admitted operation inherits the existing readiness contract and participates without a scheduler roster. Four held jobs prove capacity; releasing just one admits the fifth before its three peers finish. The original fixed-wave code fails that real-process regression. A failing refilled job leaves parent readiness unset and reaps every owned worker. Repeated release remains safe, including ExitStack cleanup after early retirement. Existing cancellation, unsupported-platform and parent-effect-order controls remain.

Persisted formats: none change. User pipelines, registered names, configuration, results and third-party formats remain intact. Worker objects and their release flags are internal transient resources, not serialized stores. This applies the NRA cookbook shared-algorithm and derived-view principles without introducing a behavior family or shadow lifecycle controller.
