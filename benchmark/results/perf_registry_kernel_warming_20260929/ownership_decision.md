# Registry kernel preparation ownership decision

Source: OpenHCS main fbf6b2d91, candidate branch codex/perf-registry-kernel-warming-20260929. Existing global NRA class census and the bounded source trace establish the registry service, catalog service ABC, endpoint Future owner, callable preparation operations, and family cache eligibility as the existing authorities. No new service, registry roster, endpoint Future, or kernel receipt is admitted.

Dominant measured cold compiler term: 23.712 seconds preparation / 24.655 seconds compilation; populated-cache ordinary compilation ~3.267 seconds. Existing persistent Numba cache reuse across fresh spawn processes is already demonstrated. Full catalog prototype: 13.934 seconds discovery of 266 functions, 18.319 parallel family cache population, 13.694 hydration/hooks. This is not a few-second cold end-to-end improvement: it pays shared preparation once ahead of pipeline compilation during catalog authoring, amortized over future pipelines. Mandatory eager endpoint startup and forcing a direct pipeline compile to wait for all unused catalog functions are rejected because they increase first-use latency.

Admit: the existing endpoint catalog Future calls a public catalog preparation method. Its local catalog implementation invokes the existing supervised preparation child even when metadata is already cached; registry readiness and kernel readiness are distinct. The child derives all obligations from actual admitted metadata.func declarations and reuses PreparationCacheBatch / CallablePreparation. Existing lazy endpoint catalog controls initiate this work; direct pipeline compilation retains its selected-callable preparation path. Source and cache roots come from existing process environment and import authority. Failure and cancellation propagate through the existing owned child and Future.

The registry's child launch method becomes public and all existing consumers migrate; no private-call compatibility alias is retained. The catalog ABC supplies ordinary catalog preparation for transports; the local implementation adds the registry-owned persistent preparation. No duplicated family list or backend switches. Current route does not claim that cache=False kernels transfer across processes or solve execution-only runtime.

Gates: source-checked NRA edits are syntax/revision evidence only. Tests must establish Future completion only after preparation, warm metadata still triggers child work, shared cancellation, derived family/hook ordering, and actual cross-interpreter persistent kernel reuse. Ordinary fresh-process benchmark measures production transfer and includes any first-use work. No full global semantic proof is claimed.

## Measured closure and additional obligations

The first ordinary reuse probe found three remaining cache writes: Sobel and its neighborhood helper, plus int32 shrink (warmup previously supplied bool). The second production candidate declares edge preparation on its existing nominal registry family, and replaces the expand/shrink manual two-strategy warmup roster with all admitted registered operations on point/region fixtures. The ensuing full-catalog warmup costs 53.529 seconds; a subsequent ordinary fresh endpoint compiles in 3.277 seconds, executes in 18.875 seconds, total 24.893 seconds, with 65 data loads and zero data writes and exact CSV parity. All 821 focused tests pass. This still is not a reduction of first-ever cold end-to-end time.

Worker lifetime is owned by PreparationCacheWorker, projected from existing operations: completion/failure is communicated on its owned pipe; ExitStack closes exact workers on errors/cancellation. No descendant process scan or private executor worker map is used. The dedicated registry child temporarily handles SIGTERM as cancellation and restores its handler. Each fork worker resets termination to the default so its exact owner can terminate/reap it. Live process cancellation is verified.
