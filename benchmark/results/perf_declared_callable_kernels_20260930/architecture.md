# Declared callable kernel preparation

The user asks to reduce actual execution and total pipeline time, use nominal shared algorithms, fold cache work into registry warming, preserve CellProfiler numerical tolerances and avoid duplicate authorities. The design started from main 4a9c9b3e1. Source 100f40c69 subsequently merges current main 65b2ed101 normally and uses its arraybridge 409b1e083 gitlink; actual imports for development resolve to the performance checkout. The complete NRA original-class census before design covers openhcs plus setup.py: 698 modules, 5,081 original ClassDefs, 5,069 canonical projected declarations and 12 explicitly OPEN/unprojected rows. The integrated control/candidate census covers 700/701 modules, 5,089/5,095 original classes and 5,077/5,083 projected declarations, again retaining 12 OPEN rows. Original decorators, lexical scopes, methods and ancestry remain in the full receipts; unsupported classes are not invented members.

The existing determining owners are PreparationOperation (successful process-local readiness and retry), PreparationCacheBatch/Worker (admitted work, four live fork children, completion/error/cancellation and physical release), AutoRegisterRegistryPreparation (module-scoped registry discovery), CompilerPreparedAutoRegisterFamily (registered preparation contract), CallablePreparation (lazy registry/module/callable hook effect order), and CellProfilerBackendStrategyMixin (provider preparation requirement). RegistryService/catalog persistence and the public metadata reader have separate roles; none determines that an arbitrary hook has only persistent kernel effects.

The production diagnostic on original main 4a9c9b3e1 found 12.75s of parallel registry-cache preparation followed by 13.83s of outer dispatcher work in parent hooks. Primary-object, shape, grid and expand/shrink preparation account for approximately 6.67, 3.93, 1.17 and 1.16s. Inclusive nested dispatcher events are not summable. An external four-pure-hook prototype on the same main, with four isolated empty-cache observations, changes internal compilation 28.612 → 21.825s and full CLI wall 48.563 → 41.778s. Its CSV exports are byte-identical. This establishes the route's empirical payoff, not a generic hook effect-order proof.

Admitted domain relation: these four mathematical warmups own only persistent kernel work and shared process-local readiness. They allocate representative arrays and discard results; they do not establish user artifacts, external state, GPU contexts or parent readiness from a child. The bound excludes arbitrary module/callable hooks and third-party hooks. Primary-object warmup deliberately covers declared threshold/declumping branches and integer-label dimensions; size/shape deliberately covers 2-D and 3-D. Neither coverage nor numerical algorithms are reduced to obtain a lower compilation time.

CellProfilerCallableKernelPreparation is an abstract protocol composing the existing successful-readiness and compiler-family capabilities. Each concrete operation owns the former warmup body and, through AutoRegisterMeta, its own registry. The protocol itself has no registry. Inherited __registry_key__ derives concrete membership from the declaration name; no callable allowlist or target roster is authored. CompilerPreparedAutoRegisterFamily.cache_preparation_operations determines physical cache work, and module registry discovery derives that projection. Its default preserves existing RegistryFamilyPreparation backend work; the callable kernel family projects concrete execute-only operations. The existing batch schedules those operations.

Parent registry preparation executes that same operation projection through PreparationOperation.prepare, while cache children invoke execute directly. An initial candidate acquired the inherited readiness lock in children; a real held-lock counterexample times out and reaps both children, while direct cache operations complete without acquiring that lock or marking parent readiness. Kernel readiness and generic hook completion are separate facts. A callable/module hook may change diagnostic state, so original generic hook execution remains at its original effect phase and calls the declared primitive body, even if prior cache work generated its kernels. Only the existing generic hook owner marks hook completion; it is not inferred from kernel readiness.

CellProfilerKernelCachePreparationMixin owns the common CPU / required persistent cache / empty explicit Numba cache admission algorithm. Backend strategies supply only their provider requirement; pure kernel declarations inherit the admitted requirement. CPU admission precedes lazy provider discovery, preserving the earlier non-CPU early return. An initial source stage was adjusted during review to restore that exact ordering before performance timing; a regression makes provider discovery fail if attempted on the rejected non-CPU route.

Alternative designs are rejected: reading every hook early violates tested mutation/error ordering; a new metadata flag/allowlist duplicates the warmup declaration; a second pool/scheduler duplicates process ownership and would pickle admitted local classes; one shared global callable-preparation registry would warm unrelated modules and combine the four jobs serially; moving unrelated primary-object work into shape/morphology providers gives the wrong owner. Concrete independent registries preserve module scope while inheriting discovery and readiness algorithms. The two existing exported preparation functions remain public consumers delegating to the declared obligation; their former mathematical bodies have one owner. The private standalone hooks are removed.

NRA exact-source transactions create the protocol and migrate existing bodies, share admission with the provider hook, project direct cache operations, and preserve capture/hook phases. They check source/syntax bindings, not arbitrary global behavioral equivalence. Separate gates cover lazy hook effects, CPU discovery order, real fork cache work without parent readiness or inherited readiness-lock acquisition, parent kernel readiness, failure retry, numerical exports, installed imports/live public pipeline and actual before/after latency. Existing original fixed-wave controls and unsupported-fork/cancellation tests remain relevant; no scheduler source changes here.

The existing perf_fixtures.capture_enabled authority determines side-effectful fixture mode. These callable cache operations are not admitted to children in that mode, and parent registry preparation defers them to their ordinary callable hooks. A module hook that enables capture late also retains its effect: a real shape callable hook emits its original fixtures after that module hook, even when kernels were generated earlier. Repeated generic preparation remains once-per-hook. The original premature capture-order failure is retained; no fixture-producing mode is misrepresented as cache-only work.

Maintenance experiment: add two local concrete kernel declarations in one test module. Registry discovery admits both without a scheduler or target-list edit; two real children populate their work and leave parent readiness empty. Parent registry preparation runs each once, and repeated public/callable preparation observes readiness. Independent registries prevent one module declaration from importing another obligation. A failed declaration leaves itself and enclosing module preparation retryable.

Applicable NRA cookbook patterns: section 2, public ABC/shared algorithm/irreducible hooks; section 3, registration derived from class declarations; section 4, meaningful multiple inheritance of readiness and compiler-family capabilities. The generic lazy hook reader and registry catalog remain independent owners, not compatibility paths. Persisted formats: none change. User pipelines, registered processing names, config, numerical results and third-party formats remain intact.
