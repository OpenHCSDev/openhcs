**Status:** investigation plan, not an implementation or proof of a current defect. **Pinned heads:** OpenHCS `main` `0c7b898f852a8bedc0e1bc38b93f36088d301808`, ZMQRuntime gitlink `1d3b32f4fcead23d5d2079c975eb2ae7646a1478`; issue observation at OpenHCS `fc1f946329cc74ffcd1b6a73d39591c259dea030` (same ZMQRuntime gitlink). ## Actual evidence and counterevidence

- #140 reports that a fork worker lane exception appears in the server log but `benchmark/openhcs_measured_run.py` stays in `client.wait_for_completion(execution_id)` for more than three minutes. This is a reported observation, not a clean reproduction at the current head.
- OpenHCS `openhcs/core/orchestrator/worker_execution.py:503–538` raises for a failed fork worker. `openhcs/runtime/zmq_execution_server.py:383–391,433–477` routes this request through the inherited server execution lifecycle. `benchmark/openhcs_measured_run.py:316–361` waits for the matching compile and execution IDs and requires a complete result.
- In the pinned ZMQRuntime, `src/zmqruntime/execution/server.py:276–313` catches exceptions from `execute_task` and calls `mark_failed(execution_id, str(e))`; `lifecycle.py:250–272` transitions nonterminal records under a lock; `wait_policy.py:53–98` returns an explicit FAILED result for a polled failed record. Thus **the observed hang is not explained by a simply missing FAILED branch**. It may involve a pre-terminal stall, control socket starvation, a different execution ID/process, failure outside the guarded region, or an unrelated poll behavior. None is proven.
- Pinned `wait_policy.py:100–133` retries poll errors indefinitely when a *known server process remains alive*; that is a plausible failure path to investigate, not proof it occurred. #157 presently changes `openhcs/runtime/zmq_execution_server.py` and needs crossing review.

## Required answers / provisional ownership

For one accepted execution ID, is the server record terminal, and can the client observe it within a bounded interval after a worker-side terminal exception? The execution lifecycle record in ZMQRuntime is the candidate determining owner of terminal status; the client waiter is a separate consumer and the benchmark converts an observed failure to a durable failed row. Do not make a benchmark-only timeout masquerade as server failure propagation. The remote server protocol and execution IDs are separate identities from a local process PID. `R*` is provisional: server-failure → matching record FAILED → waiter reports that same failure → benchmark row records its message; cancellation, delayed healthy work, and transient network loss require distinct answers. No class-family or behavioral-equivalence claim is admitted from this issue report alone.

## Investigation and acceptance gates

1. In an isolated pinned worktree with recorded dependency SHAs, inject a deterministic fork-worker exception through ordinary ZMQ submission. Capture execution ID, server lifecycle record transitions, status responses, progress sequence, server liveness and waiter outcome under one bounded external deadline; preserve logs. Reproduce the specific #140 hang or identify why current source behaves correctly before writing a fix.
2. If record stays RUNNING, locate the worker→server completion owner and fix its terminal transition. If record is FAILED but client cannot see it, locate the control/status transport owner. If polling throws while an alive server is stuck, determine a bounded retry/liveness policy without declaring long legitimate executions failed. Cross-check pinned ZMQRuntime source and tests before any dependency PR; no duplicate status cache in OpenHCS.
3. Test a worker failure, healthy long execution, explicit cancellation, transient status error, and server-process loss. Assert matching IDs, actionable error text, bounded waiter termination after actual terminal failure, and a durable failed benchmark row. Do not weaken genuine long-running support to pass a timeout test.
4. Reinspect PR #157's head for collisions. A full context NRA scan with `scan_status`, class-first syntax rows and raw record evidence is required before *prescribing a structural refactor*; no such scan was completed for this plan. A focused root `openhcs/runtime` census/overlay at this head has 18,078 code lines and heuristic findings, none of which proves this failure path.

**Decision point:** if the injected failure already terminates correctly at the pinned head, document closure evidence instead of adding a redundant fix. If not, name the exact owner and open a separate implementation PR. This draft plan does not close #140.
